먼저 결정해 주셔야 하는 것 4가지

  1. 재화 이름을 조개로 확정할지 리서치 1순위는 물고기였지만 씬에 물고기 3D가 없다. 물고기로 가면 신규 3D 제작 1건이 MVP 일정에 추가된다. 조개는 이미 해변에 렌더돼 있어 2D 아이콘 1장이면 끝난다. → 2절
  2. 키캡 4칸 재배치안(CAT / DESK / WORK / STATUS+LOG)을 받아들일지 1·2번을 고양이·자리꾸미기로 쓰면 기존 세션연결·진행상황·활동기록 3개가 2칸에 들어가야 한다. 세션연결은 업무지시와 묶어 3번으로 통합하는 안이다. 최근의 "키캡 4키만 남기는 미니멀 방향"과 충돌하는지 확인이 필요하다. → 3절
  3. 워크스테이션 3종(seat-1/3/4)의 로컬 좌표 실측을 언제 할지 소품을 책상 어디에 얹을지 정하는 앵커 좌표가 코드 어디에도 없다. 자리 꾸미기 구현의 최대 리스크 지점이고, 실측 전에는 seat-2 외 좌석 작업을 시작할 수 없다. → 12절
  4. 고양이 스타일을 좌석별로 따로 줄지 지금은 스타일·체형이 전역 단일 상태라 좌석 4개가 전부 같은 모습으로 보인다. 좌석별 개별화는 좌석마다 FBX를 따로 로드하는 큰 리팩터(L)가 선행돼야 한다. → 4절

아래 본문은 위 4가지를 조개 / 재배치 수용 / 실측은 MVP 안에서 / 좌석별 개별화는 3단계 폴리시로 가정하고 쓴 것이다. 결정이 달라지면 해당 절만 갈아끼우면 된다.

1. 한 장 요약

무엇을 만드는가: 3D 해변 사무실에서 Codex 세션이 곧 고양이 1마리로 사는 이 앱에, (1) 고양이를 꾸미고 이름 짓고 간식 주는 "고양이 관리" 기능과 (2) 좌석(워크스테이션)을 화분·머그컵·키캡키보드·쿠션·의자로 단계별로 꾸미는 "자리 꾸미기" 기능을 추가한다. 지금 하단 키캡 4개는 코드는 다 있지만 SHOW_LEGACY_OVERLAYS 플래그에 가려 아무 것도 뜨지 않는 상태다 — 이 게이트를 부분 해제하는 게 모든 작업의 0순위 선행 조건이다.

왜 만드는가: 이미 있는 acorns(도토리) 재화는 task 완료마다 쌓이기만 하고 쓸 곳이 전혀 없는 표시 전용 값이다. 이걸 실제로 쓸 수 있는 재화로 승격시키고, 그 소비처로 사용자가 음성으로 요청한 고양이 커스터마이징과 자리 꾸미기를 붙인다.

최종 재화 이름 결론: 조개(Shell). 도토리는 숲/다람쥐 세계관 전용이라 고양이+해변 배경과 안 맞고, 물고기는 근거는 좋지만 뒷받침할 3D 자산이 없다. 조개는 해변 씬에 이미 실물 3D 클러스터(shoreline-rock-starfish-shell-cluster)가 배치돼 있어 신규 3D 자산 없이 2D 아이콘 1장만으로 개명이 끝난다.

3. 하단 키캡 4칸 최종 배치안

선행 조건

app/page.tsx의 SHOW_LEGACY_OVERLAYS = false 플래그가 cats/sessions/status/activity 4탭이 든 <aside className="radio-panel"> 전체를 가리고 있어, 지금은 키캡을 눌러도 패널이 안 뜬다. 이 조건문에서 SHOW_LEGACY_OVERLAYS && 부분만 제거해 패널을 되살린다(상수 선언 자체는 유지 — 테스트가 상수 선언 문자열만 단언하고 있어 안 깨짐). 이 1줄 변경 없이는 이하 모든 UI 작업이 화면에 나타나지 않는다.

4. F1 고양이 패널

고양이 추가

'고양이 추가하기'는 곧 Codex 세션 페어링이다(세션 1개 = 좌석 1개 = 고양이 1마리, 최대 4마리 동시 접속·5번째부터 대기열). 버튼은 3번 WORK 탭으로 이동시키며, 별도 오버레이나 모달을 새로 만들지 않는다 — 기존 탭 이동 패턴을 그대로 재사용해 구현 비용을 낮춘다.

이름 짓기

텍스트 인풋 1개 + '다른 이름 추천' 버튼. 기본 추천 이름 풀 20개(기존 부서 기본이름 모모/토토/보리/코코와 중복 없음):

글자수 제한 6자. 3D 이름표 캔버스 팻말은 폭 368px·폰트 34px 고정이라 14자를 다 채우면 팻말 밖으로 넘친다. 한글 6자(약 192px)가 안전 수납 한도라 입력창 maxLength를 6으로 제한한다. 새 좌석이 배정되는 순간 런타임키 해시로 이름 풀에서 결정론적으로 하나가 즉시 배정돼, '이름 없는 상태'가 생기지 않는다.

스타일 변경

15종(아비시니안/검은고양이/턱시도/블루/밥테일/브리티시숏헤어/크림/메인쿤/페르시안/레드/치즈흰얼룩/샴/심플/스핑크스/화이트) 전부 무료, 즉시 변경(2절 최종 결론). 단, 현재 구조상 고양이 스타일·체형은 좌석별이 아니라 전역 단일 상태라 좌석 4개가 다 같은 모습으로 보인다 — 이 제약을 패널에 "지금은 모든 고양이에게 같은 모습이 적용됩니다" 문구로 명시 고지한다. 좌석별 개별화는 좌석별 FBX 로드 리팩터링(폴리시 단계, 3D/아트 목록 9절 참고)이 선행돼야 한다.

체형

4단계(원래대로/살짝/통통/뚱냥이) 라디오 선택, 이미 코드에 연결·적용된 fattenCat() 파이프라인을 그대로 노출만 하면 된다. 간식 누적 급여량이 임계치(5/15/30회)를 넘으면 다음 단계를 토스트로 '추천'만 하고 강제 변경은 하지 않는다.

구조 원칙

"자리 꾸미기 단계"는 이 desk 위에 얹는 소품 슬롯의 개방 개수를 나타내는 별도의 순수 데이터 값(0~4)으로 구현하며, 소품은 desk Group의 자식 오브젝트(desk-local 좌표)로만 부착한다 — 이미 검증된 유일한 production 부착 패턴이라 씬 전체 절대좌표 재계산이 필요 없다. 로우모니터 좌석(seat-2)의 desk GLB는 단일 텍스처로 통짜 베이크돼 있어 내부 부품(쿠션 등) 분리·교체가 불가능하고, 나머지 3개 좌석도 마찬가지일 가능성이 높아(실측 필요) 이 원칙을 전 좌석에 동일하게 적용한다.

소유 vs 배치

아이템 구매(소유)는 계정 전역 1회, 티어 진행과 배치(장착)는 좌석별 개별이다. desk 형상 자체가 좌석마다 달라 배치 좌표를 공유할 수 없고(기술적 강제), 반대로 좌석마다 새로 사야 한다면 같은 아이템을 4번 사는 그라인드가 생기기 때문이다.

11. 도구 신뢰를 지키는 규칙

  • 버프 없음: 자리 꾸미기·스타일·체형·간식 어느 것도 작업 속도·성공률·토큰 절약에 영향을 주지 않는다. AgentStatus에 그런 수치 필드 자체가 없고, 만들지도 않는다.
  • 작업 방해 금지: 아이들 이벤트는 대기 상태(idle/completed/failed) 전용 루프에만 얹혀 있어, 작업 중에는 물리적으로 실행되지 않는 구조로 보장한다. 별도 억제 로직을 새로 만들지 않는다.
  • 손실형 장치 금지: 스트릭(연속 접속) 방식은 쓰지 않는다. 접속 보너스·출석 마일스톤 모두 누적 총량제로, 하루 빠져도 이전 기록이 사라지지 않는다.
  • 놓쳐도 손해 없음: 방치 상태에서도 아이들 이벤트 기본 보상은 반드시 지급되고, 클릭은 보너스일 뿐 필수가 아니다. 유일하게 클릭이 필요한 택배상자도 열기 전까지 사라지지 않는다.
  • 경고·타이머·상시 배지 지양: 토스트 팝업, 빨간 카운트다운, '놓치면 사라짐' 문구는 쓰지 않는다.
  • 결제 경로 없음: 조개를 현금으로 사는 경로는 절대 만들지 않는다(향후 유료화가 논의되더라도 이 경계는 유지).
  • 치팅 대응 수준: localStorage 값을 devtools로 직접 조작하는 것은 막지 않는다 — 서버 계정이 없어 원천적으로 검증 불가능하고, 현금화 경로도 없어 조작해도 타인 피해가 없다. 다만 오프라인 트리클은 시계 조작 악용을 줄이기 위해 클라이언트 clamp(최대 12시간)를 적용한다.
  • 온보딩·접근성·모바일 대응은 이번 스펙 범위를 최소한으로만 다룬다: 최초 접속 시 조개 소량 웰컴 지급과 상점 최초 진입 시 1회성 툴팁 정도만 기본값으로 두고, 등급 배지는 색상만이 아니라 텍스트도 함께 표기한다. 모바일 반응형은 이 앱이 데스크톱 3D 뷰 중심이라 이번 스펙 범위 밖으로 둔다(12절 미결 질문 참고).

도출된 설계 원칙

  • 획득 채널 최상위는 '실제 도구 사용'(세션 완료=task.completed) 이어야 함. 게임화가 도구 본질 대체하면 안 됨 — 전체 수급의 40% 이상을 여기 배정.
  • 손실형 연속출석(스트릭) 금지. Duolingo/Habitica 사례처럼 '끊기면 보너스 소멸' 방식은 불안·이탈 유발. 대신 누적형(총 접속일수 7/30/100일 마일스톤) 채택 — 손실 없고 되돌아와도 불이익 없음.
  • 일일 첫 접속 보상은 '그날 처음 켰을 때 flat 지급' 수준으로 얕게. 강제 접속 유도 프레이밍(경고·타이머·빨간 배지) 금지, '선물함' 톤 유지.
  • 오프라인/방치 트리클은 상한 캡(12시간 권장) 두고 전체 수급의 10% 이하 보조 채널로만. localStorage 타임스탬프라 시계조작 치팅 원천봉쇄 불가하나, 판돈 작게 설계하면 치팅 실익 없음 — 서버검증 없이 클라이언트 clamp(음수/과대 elapsed 배제)면 충분.
  • Idle 이벤트(비둘기 쫓기·낮잠 등)는 탭 없이 대기 애니메이션 중 랜덤 트리거되는 보상으로. Neko Atsume식 '안 봐도 알아서 쌓임' 원칙 — 강제 체류시간 요구 안 함.
  • 재화는 단일 소프트 재화 유지. 무과금 도구 앱이라 하드/프리미엄 재화(다이아) 도입 불필요·역효과. 이미 있는 ACORN을 코인 역할로 확장 사용 — 별도 화폐 신설보다 리스크 적음.
  • 다이아몬드·하트는 피할 것: 다이아는 '결제 유도/프리미엄' 뉘앙스라 무과금 도구 신뢰 훼손, 하트는 보통 '목숨/에너지 제한' 의미로 오인되어 좌절감 유발.
  • 첫 구매 경험은 첫 세션(5~10분) 내 가능하게: 시작 시 소량 시드 지급 + 최저가 티어1 아이템은 즉시 구매 가능한 가격으로 설정. 초반 5~10분 이탈률 40~60%라는 온보딩 통계 근거.
  • 업그레이드 티어는 무한 지수형(클리커식) 아닌 유한 4~6단계, 비용배율 1.5~1.8배 지수곡선. 매 티어마다 외형 변화 눈에 띄게(코지 게임 UX 원칙).
  • 마일스톤/업적(첫 고양이 연결, 5마리 모으기 등)은 일회성 큰 지급으로 목표감 부여 — 반복 수급과 별개 채널.
  • 재화 이름은 마스코트+배경(비오옴)과 직결돼야 한다 — 도토리(숲/다람쥐 상징)를 고양이 마스코트+해변/무인도 배경에 쓰면 즉각적 테마 불일치가 발생한다. Idle Acorns/Squirrel Idle Tycoon처럼 '도토리'가 성공한 사례는 전부 숲·다람쥐 세계관에서였다.
  • 하트·별·다이아몬드는 업계 관습상 이미 고정된 의미를 갖는다 — 하트=라이프/호감도, 별=등급·프리미엄 티어, 다이아몬드=유료 하드커런시. 이 관습을 깨고 소프트 재화로 쓰면 유저가 재화 기능을 오인한다(예: 하트를 보면 '이거 다 쓰면 게임 오버?'라고 생각).
  • 결제(IAP)가 없는 게임은 소프트/하드 이중재화를 나눌 이유가 없다 — 이중재화(Neko Atsume 은/금 물고기, Merge Mansion 코인/젬)의 존재 목적은 과금 유도·타임스킵 판매인데, 이 게임엔 그 축이 없다. 단일 재화 + 희귀 등급 변형(마일스톤 보상용) 정도면 충분하다.
  • Cats & Soup처럼 재화를 용도별로 분리(골드=코어루프, 가구코인=꾸미기 전용, 레시피포인트=성장)하면 이름만 보고 용도가 예측되는 정보 스캔 효과가 생긴다. 다만 무과금 소규모 게임에선 재화 종류를 늘리기보다 기존 단일 재화의 소비처(간식/꾸미기)를 다양화하는 편이 관리 비용 대비 효율적이다.
  • 디제틱(diegetic) 재화가 몰입을 깨지 않는다 — Neko Atsume은 '고양이가 고마움의 표시로 물고기를 놓고 감'이라는 세계관 내적 설명이 가능해서 자연스럽다. 이 게임은 고양이+해변이므로 '물고기'가 세계관 안에서 설명 가능한 유일한 후보다(도토리는 해변에 존재할 이유가 없음).
  • 재화 이름은 곧 아이콘 디자인 방향을 결정한다 — 이름을 먼저 확정해야 아이콘 제작 후 재작업(리네임에 따른 리아이콘)을 피할 수 있다.
  • 기존 재화 데이터가 이미 쌓여 동작 중이라면 '폐기'보다 '개명(라벨·아이콘 교체 + 값 이전)'이 저비용·저리스크다 — 로직(적립 트리거, HUD 표시)은 그대로 두고 표시명/아이콘/스토리지 키만 바꾸면 유저 데이터 손실 없이 테마 불일치를 해소할 수 있다.

  • currency.json 1절 vs workstation.json/cats.json/idle.json 전체
    재화 이름과 localStorage 키가 스펙마다 다름 — currency.json은 "조개"(CURRENCY_KEY=agent-forest-shell-v1)로 확정했는데, workstation.json·cats.json·idle.json은 전부 "물고기"(FISH_KEY=agent-forest-fish-v1)를 채택함. 4개 스펙이 같은 프로젝트의 재화를 서로 다른 이름·키로 구현하게 됨.
    → 반영: currency.json이 최종안이라면 workstation/cats/idle 세 문서의 FISH_KEY·"물고기" 표기를 전부 CURRENCY_KEY·"조개"로 통일. 반대로 물고기가 최종이면 currency.json을 갱신. 4개 문서 중 하나를 single source of truth로 지정 후 나머지 3개를 종속 갱신할 것.
  • currency.json 4절(스타일 해금) vs cats.json 3절(스타일 변경)
    currency.json은 스타일 15종을 커먼60/레어100/에픽160 조개로 유료 해금하도록 설계했는데, cats.json은 같은 15종을 "전부 무료, 즉시 변경"으로 결론짓고 재화 게이팅 자체를 배제하는 근거까지 제시함. 정반대 결론.
    → 반영: 스타일 해금이 유료 소모처인지 여부를 먼저 확정하고, 채택 안 된 쪽 스펙(currency.json의 STYLE_UNLOCK_PRICE 절 또는 cats.json 3절의 '전부 무료' 결론)을 삭제·수정.
  • currency.json 8절 vs workstation.json 0절/구현1 vs cats.json 6절/구현1
    4개 키캡(탭) 최종 구조가 3개 스펙마다 다름. currency.json은 기존 4탭(cats/sessions/status/activity)이 그대로 유지된다고 가정. workstation.json은 2번만 workstation-decor로 바꾸고 sessions는 1번(cats) 탭 하위로 흡수. cats.json은 4탭을 CAT/DESK/WORK/STATUS+LOG로 전면 재정의하며 sessions를 3번(WORK) 탭에 합침. 세션 화면이 갈 곳이 스펙마다 다르고(1번 vs 3번), status/activity 병합 여부도 다름.
    → 반영: IA(정보구조) 오너가 최종 탭 레이아웃 1안을 확정하고 나머지 두 스펙을 그 안에 맞춰 재작성. 최소한 sessions·status·activity 세 화면의 최종 위치를 표로 통일해 3개 문서에 동일하게 반영.
  • currency.json dataModel(SEAT_DECOR_TIER_KEY) vs workstation.json dataModel(WORKSTATION_DECOR_KEY)
    자리 꾸미기 이코노미가 두 스펙에서 완전히 다르게 설계됨. currency.json: 티어당 가격 40/70/120/200(누적), 아이템 4종 고정(화분/머그컵/데스크매트+미니키캡/담요), 저장키 SEAT_DECOR_TIER_KEY(값=0~4 정수). workstation.json: 티어 진입비 20/60/140/260, 16종 개별 구매 카탈로그, 저장키 WORKSTATION_DECOR_KEY(ownedItemIds+seats 객체). 가격도 아이템 수도 데이터 모델도 안 맞고, 사용자가 요청한 '쿠션'과 '의자'는 currency.json의 4종 목록에는 아예 없음(workstation.json에만 있음).

    간식 카탈로그가 스펙마다 다름 — currency.json: 기본캔참치(무료,1일1회)/훈제연어15/그레인프리25. cats.json: 츄르3/캔사료6/츄르세트12, 무료 항목 자체가 없음. 이름·가격·무료여부 전부 불일치.

    '가만히 있는 유저'가 '실제로 작업 1건 한 유저'보다 더 번다. 계산: 완전 방치(탭만 열어두고 클릭 0회) = dailyLogin(10) + idleNap 상한(16) + idleChase 상한(15) + offlineTrickle 상한(12) = 53개/일. currency.json 자신의 '라이트 유저' 시나리오(작업 1건 포함) = task(5)+daily(10)+nap(2)+chase(3)+offline(12) = 32개/일. 즉 진짜 작업을 1건 한 유저(32)가 아무것도 안 한 유저(53)보다 65.6% 적게 번다. 손익분기점 계산: 실작업 수입(5×N)이 완전방치 수입(nap+chase 상한 31)을 넘으려면 N≥7건/일 필요(7×5=35>31, 6건으로는 30<31로 부족) — 그런데 스펙 자신의 라이트 페르소나는 1건/일이라 절대 못 넘는다. idle.json은 낮잠·한눈팔기를 '완전 방치형', '자동완료'로 명시했고 settling(4~10초)·kneading(7초) 주기가 짧아(완주기 약 12~20초) 탭을 15~30분만 열어둬도 이 상한에 도달한다 — 이 앱은 에이전트 작업 상태를 지켜보는 대시보드이므로 '탭을 켜두고 지켜만 보는 것'은 예외적 어뷰징이 아니라 기본 사용 패턴이다. currency.json이 스스로 명시한 설계원칙('실사용 도구 사용이 최상위 채널이어야 한다')과 정면으로 모순된다.
    → 반영: idleNap/idleChase의 일일 상한을 task 최소 기대치(라이트 유저 1건=5개) 이하로 낮추거나(예: 낮잠+한눈팔기 합산 상한을 20개 이하로), 반대로 task 보상을 상향(예: 8개/건)해 N=7 손익분기점을 N=1~2 수준으로 끌어내린다. 동시에 offlineTrickle·dailyLogin처럼 '클릭 없이 나오는' 채널의 합산 상한이 실작업 채널의 하루 기대 수입을 넘지 않도록 상한 재설계.
  • cats 스펙 §3 vs currency 스펙 §4(소모처) — 고양이 스타일 15종 유료화 여부
