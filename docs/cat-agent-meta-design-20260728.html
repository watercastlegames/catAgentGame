1부 조개 경제와 하단 메뉴 재설계

1. 한 장 요약

무엇을 만드는가: 3D 해변 사무실에서 Codex 세션이 곧 고양이 1마리로 사는 이 앱에, (1) 고양이를 꾸미고 이름 짓고 간식 주는 "고양이 관리" 기능과 (2) 좌석(워크스테이션)을 화분·머그컵·키캡키보드·쿠션·의자로 단계별로 꾸미는 "자리 꾸미기" 기능을 추가한다. 지금 하단 키캡 4개는 코드는 다 있지만 SHOW_LEGACY_OVERLAYS 플래그에 가려 아무 것도 뜨지 않는 상태다 — 이 게이트를 부분 해제하는 게 모든 작업의 0순위 선행 조건이다.

왜 만드는가: 이미 있는 acorns(도토리) 재화는 task 완료마다 쌓이기만 하고 쓸 곳이 전혀 없는 표시 전용 값이다. 이걸 실제로 쓸 수 있는 재화로 승격시키고, 그 소비처로 사용자가 음성으로 요청한 고양이 커스터마이징과 자리 꾸미기를 붙인다.

최종 재화 이름 결론: 조개(Shell). 도토리는 숲/다람쥐 세계관 전용이라 고양이+해변 배경과 안 맞고, 물고기는 근거는 좋지만 뒷받침할 3D 자산이 없다. 조개는 해변 씬에 이미 실물 3D 클러스터(shoreline-rock-starfish-shell-cluster)가 배치돼 있어 신규 3D 자산 없이 2D 아이콘 1장만으로 개명이 끝난다.

선행 조건

고양이 추가

'고양이 추가하기'는 곧 Codex 세션 페어링이다(세션 1개 = 좌석 1개 = 고양이 1마리, 최대 4마리 동시 접속·5번째부터 대기열). 버튼은 3번 WORK 탭으로 이동시키며, 별도 오버레이나 모달을 새로 만들지 않는다 — 기존 탭 이동 패턴을 그대로 재사용해 구현 비용을 낮춘다.

이름 짓기

텍스트 인풋 1개 + '다른 이름 추천' 버튼. 기본 추천 이름 풀 20개(기존 부서 기본이름 모모/토토/보리/코코와 중복 없음):

나비 · 두부 · 콩이 · 초코 · 모카 · 딸기 · 만두 · 몽실이 · 호두 · 감자 · 뭉치 · 요롱이 · 미미 · 까망이 · 노랑이 · 흰둥이 · 마루 · 순두부 · 방울이 · 나옹이

글자수 제한 6자. 3D 이름표 캔버스 팻말은 폭 368px·폰트 34px 고정이라 14자를 다 채우면 팻말 밖으로 넘친다. 한글 6자(약 192px)가 안전 수납 한도라 입력창 maxLength를 6으로 제한한다. 새 좌석이 배정되는 순간 런타임키 해시로 이름 풀에서 결정론적으로 하나가 즉시 배정돼, '이름 없는 상태'가 생기지 않는다.

스타일 변경

15종(아비시니안/검은고양이/턱시도/블루/밥테일/브리티시숏헤어/크림/메인쿤/페르시안/레드/치즈흰얼룩/샴/심플/스핑크스/화이트) 전부 무료, 즉시 변경(2절 최종 결론). 단, 현재 구조상 고양이 스타일은 좌석별이 아니라 전역 단일 상태라 좌석 4개가 다 같은 모습으로 보인다 — 이 제약을 패널에 "지금은 모든 고양이에게 같은 모습이 적용됩니다" 문구로 명시 고지한다. 좌석별 개별화는 좌석별 FBX 로드 리팩터링(폴리시 단계, 3D/아트 목록 9절 참고)이 선행돼야 한다.

5. F2 자리 꾸미기

구조 원칙

워크스테이션 GLB 4종(텐트형/원형 노트북/접이식 노트북+라디오/로우모니터+키캡)은 좌석마다 다른 형상으로 고정 배정된 종류이지 승급 가능한 티어가 아니다 — 절대 갈아 끼우지 않는다. "자리 꾸미기 단계"는 이 desk 위에 얹는 소품 슬롯의 개방 개수를 나타내는 별도의 순수 데이터 값(0~4)으로 구현하며, 소품은 desk Group의 자식 오브젝트(desk-local 좌표)로만 부착한다 — 이미 검증된 유일한 production 부착 패턴이라 씬 전체 절대좌표 재계산이 필요 없다. 로우모니터 좌석(seat-2)의 desk GLB는 단일 텍스처로 통짜 베이크돼 있어 내부 부품(쿠션 등) 분리·교체가 불가능하고, 나머지 3개 좌석도 마찬가지일 가능성이 높아(실측 필요) 이 원칙을 전 좌석에 동일하게 적용한다.

소유 vs 배치

아이템 구매(소유)는 계정 전역 1회, 티어 진행과 배치(장착)는 좌석별 개별이다. desk 형상 자체가 좌석마다 달라 배치 좌표를 공유할 수 없고(기술적 강제), 반대로 좌석마다 새로 사야 한다면 같은 아이템을 4번 사는 그라인드가 생기기 때문이다.

11. 도구 신뢰를 지키는 규칙

  • 버프 없음: 자리 꾸미기·스타일·간식·욕구 시스템 어느 것도 작업 속도·성공률·토큰 절약에 영향을 주지 않는다. AgentStatus에 그런 수치 필드 자체가 없고, 만들지도 않는다.
  • 작업 방해 금지: 아이들 이벤트는 대기 상태(idle/completed/failed) 전용 루프에만 얹혀 있어, 작업 중에는 물리적으로 실행되지 않는 구조로 보장한다. 별도 억제 로직을 새로 만들지 않는다.
  • 손실형 장치 금지: 스트릭(연속 접속) 방식은 쓰지 않는다. 접속 보너스·출석 마일스톤 모두 누적 총량제로, 하루 빠져도 이전 기록이 사라지지 않는다.
  • 놓쳐도 손해 없음: 방치 상태에서도 아이들 이벤트 기본 보상은 반드시 지급되고, 클릭은 보너스일 뿐 필수가 아니다. 유일하게 클릭이 필요한 택배상자도 열기 전까지 사라지지 않는다.
  • 경고·타이머·상시 배지 지양: 토스트 팝업, 빨간 카운트다운, '놓치면 사라짐' 문구는 쓰지 않는다.
  • 결제 경로 없음: 조개를 현금으로 사는 경로는 절대 만들지 않는다(향후 유료화가 논의되더라도 이 경계는 유지).
  • 치팅 대응 수준: localStorage 값을 devtools로 직접 조작하는 것은 막지 않는다 — 서버 계정이 없어 원천적으로 검증 불가능하고, 현금화 경로도 없어 조작해도 타인 피해가 없다. 다만 오프라인 트리클은 시계 조작 악용을 줄이기 위해 클라이언트 clamp(최대 12시간)를 적용한다.
  • 온보딩·접근성·모바일 대응은 이번 스펙 범위를 최소한으로만 다룬다: 최초 접속 시 조개 소량 웰컴 지급과 상점 최초 진입 시 1회성 툴팁 정도만 기본값으로 두고, 등급 배지는 색상만이 아니라 텍스트도 함께 표기한다. 모바일 반응형은 이 앱이 데스크톱 3D 뷰 중심이라 이번 스펙 범위 밖으로 둔다(12절 미결 질문 참고).

가독성 보호: sulky 연출은 isAutonomous(idle/completed/failed) 상태에서만 적용되므로, 실제 작업 중(working)인 좌석의 표시(status-lamp 등)와 절대 겹치지 않는다 — 이 구조적 분리가 이미 존재하므로 별도 게이트를 추가하지 않아도 안전하다.

필수 회귀 테스트: "happiness 값과 무관하게 startTask 호출이 즉시 발생한다"를 검증하는 단위테스트를 신규 추가한다(§13 로드맵에 반영) — 향후 리팩터링 중 이 경계가 실수로 깨지는 것을 잡아내는 유일한 안전망이다.

9. 구글 연동 DB 동기화 기획

인증 경로 — 확정 전 반드시 먼저 확인할 사항: 실측 결과 이 프로젝트는 이미 OpenAI 호스팅 플랫폼에 배포돼 있고(.openai/hosting.json에 D1 바인딩 연결 확인됨), app/chatgpt-auth.ts가 oai-authenticated-user-email 헤더 기반 사용자 식별 메커니즘을 이미 갖고 있다(현재는 어디서도 import되지 않는 죽은 코드이지만 배선 자체는 존재). 반면 완전 신규 Google OAuth를 커스텀 구축하려면 redirect_uri로 쓸 실제 도메인과 호스팅 컨트롤플레인이 커스텀 콜백 경로를 허용하는지가 미확인이다.

결론: 두 경로 중 하나로 확정하지 않고, 다음을 먼저 조사한 뒤 결정한다(§14 미결질문에도 등록) — (a) 이 앱이 ChatGPT 클라이언트 안에서 열리는 용도라면 chatgpt-auth.ts를 되살리는 쪽이 신규 인프라 없이 훨씬 저비용, (b) 정말 별도 Google 계정 로그인이 필요하다면 호스팅 도메인 확인 후 OAuth2+PKCE+jose(JWT검증, Workers 호환 확인 필요)로 신규 구축. DB 스키마는 users 테이블에 googleSub·oaiUserEmail 두 식별자 컬럼을 모두 갖도록 설계해 어느 쪽이 채택되든 재작업이 최소화되게 했다(dataModel 참고).

테이블 스키마: users/user_sessions/player_shell_delta_log/cat_need_state(threadId 키잉)/workstation_decor_state 등 — 전체 정의는 dataModel 참고. 기존 db/schema.ts의 relay_* 5테이블은 브릿지 페어링 전용이라 그대로 두고 손대지 않는다.

12-2. UI 사운드 원칙 5가지

1. 열림=상승, 닫힘=하강(피치 컨투어 대칭) — 사용자의 공간적 멘탈모델에서 '나타남'은 위로 떠오르는 느낌, '사라짐'은 가라앉는 느낌과 자연스럽게 대응한다. 열기·닫기를 정확히 역방향 글리산도로 만들면 사용자가 두 소리를 하나의 '짝'으로 학습하기 쉽고, 눈을 안 봐도 지금 열렸는지 닫혔는지 구분된다. 2. 재질감의 세계관 일치 — 이 앱은 해변/캠핑 테마고 기존 음원(KBD_Thock_Type_Loop_01=나무 타건, AMB_Beach=갈매기·파도)이 전부 아날로그·자연물 질감이다. 신규 UI음이 신스 비프음이면 그 순간만 다른 앱처럼 들린다 — 나무/조개/모래/유리 재질로 통일해야 세계관이 안 깨진다. 3. 성공/실패의 청각적 즉시 구분(반응·성패 대비) — 이 앱은 실사용 개발 도구라 사용자가 다른 창을 보고 있을 때도 작업 결과를 들어야 한다. 성공은 상승+배음 풍부(화사함), 실패는 하강+감쇠 큼(둔탁함)으로 극단적으로 대비시켜야 텍스트를 안 읽고도 성패를 안다. 4. 길이는 조작 빈도에 반비례 — 탭 전환·키캡 클릭처럼 자주 누르는 조작은 100ms 이하로 짧게, 마일스톤처럼 드문 이벤트는 900ms까지 길게 허용한다. 그래야 잦은 조작이 소리로 인해 답답해지지 않는다. 5. 드문 이벤트에만 잔향(reverb) 허용 — 나머지 큐는 전부 '잔향 없음'으로 명시했는데, 이는 반복 재생 시 잔향이 겹쳐 뭉개지는 걸 막기 위함이다. 마일스톤처럼 세션당 몇 번 안 울리는 이벤트에만 예외적으로 짧은 잔향(300ms)을 허용해 '특별함'을 표현한다.

12-4. 동시 재생·연타 처리

기존 keycap 패턴(재사용 가능하지만 한계 있음): keycapAudioPoolRef(app/page.tsx:346)는 HTMLAudioElement 2개를 만들어 keycapAudioIndexRef.current % audioPool.length로 라운드로빈 재생한다(1285-1291행). 이 방식은 일반 <audio> 태그가 자기 자신과 겹쳐 재생할 수 없어서 필요했던 우회책이다.

중요 발견(버그): pressRadioMenuKey(app/page.tsx:1283-1300) 안 어디에도 audioEnabled 체크가 없다 — .sound-toggle로 소리를 꺼도(setAudioEnabled(false), worldAudioRef의 master gain만 내림) 키캡 클릭음은 그대로 재생된다. 이는 world-audio.ts의 AudioContext/master 체계 밖에 있는 별도 경로이기 때문이다.

신규 UI 사운드는 이 우회책을 반복하지 않는다: world-audio.ts는 이미 AudioBufferSourceNode 방식을 쓰는데(playCat, 266-283행), 이 방식은 매 호출마다 새 source 노드를 만들어 같은 버퍼를 여러 번 동시에 겹쳐 재생할 수 있다 — 풀링이 원천적으로 불필요하다. 따라서: 1. 키캡 클릭도 playUi("keycapClick")로 이관해 enabled/unlocked 게이팅을 자동으로 물려받는다(버그 해결). 2. 연타(예: 탭을 초당 5회 이상 누름) 대비, 큐별 최소 재트리거 간격(retrigger floor)만 하나 둔다 — 예: 40ms 이내 같은 큐 재호출은 무시(lastUiPlay: Map<UiCue, number>로 context.currentTime 비교). 이는 여러 소스가 겹쳐 소리가 뭉개지는 것(“기관총” 소음)을 막기 위한 최소 안전장치일 뿐, 기존 2버퍼 라운드로빈 같은 복잡한 풀은 필요 없다.

12-5. 효과음 조달 경로

기존 12개 월드 오디오 중 해변 앰비언스 3종·키보드 타건·고양이 콜 4종·BGM 1종은 ElevenLabs(eleven_text_to_sound_v2, prompt_influence 0.75) 생성물이고 Suno BGM 1개, 별도 CC 라이선스 표기가 없는 자체 생성물 취급이다(public/audio/ATTRIBUTION.txt). 반면 keycap-click 2종만 Freesound CC0 실물 녹음이다.

결론: 신규 UI SFX 12종은 sfx-voice-gen(Freesound CC0/CC-BY) 경로로 간다. 근거:

  • ElevenLabs 생성음은 유기적이지만 톤이 은은하게 '합성감 있는 매끄러움'을 갖는 경향이 있고, UI 클릭류처럼 짧고 물리적 타격감이 명확해야 하는 소리는 실제 녹음(Freesound)이 재질감을 더 정확히 표현한다.
  • keycap-click 2종이 이미 Freesound CC0 실물이라 신규 UI음도 같은 출처로 맞추면 '탭 전환→키캡 클릭'처럼 인접해 재생되는 소리끼리 질감 이질감이 없다.
  • 라이선스 관리가 이미 ATTRIBUTION.txt 파일로 서식화돼 있어 CC0/CC-BY 신규 항목 추가가 절차적으로 쉽다.
  • ElevenLabs 재생성은 매번 미세하게 다른 결과물이 나와 이미 확정된 12개 파일과 신규 12개 사이 스타일 재현성이 떨어진다.

playUi(cue: UiCue) {

    if (!buffer || !ctx || !master || !enabled || !unlocked) return;
    const gain = ctx.createGain();
    gain.gain.value = UI_CUE_VOLUME[cue];
    const source = ctx.createBufferSource();
    source.buffer = buffer;
    source.connect(gain).connect(master);
    source.start();
  });
},

도출된 설계 원칙

  • 획득 채널 최상위는 '실제 도구 사용'(세션 완료=task.completed) 이어야 함. 게임화가 도구 본질 대체하면 안 됨 — 전체 수급의 40% 이상을 여기 배정.
  • 손실형 연속출석(스트릭) 금지. Duolingo/Habitica 사례처럼 '끊기면 보너스 소멸' 방식은 불안·이탈 유발. 대신 누적형(총 접속일수 7/30/100일 마일스톤) 채택 — 손실 없고 되돌아와도 불이익 없음.
  • 일일 첫 접속 보상은 '그날 처음 켰을 때 flat 지급' 수준으로 얕게. 강제 접속 유도 프레이밍(경고·타이머·빨간 배지) 금지, '선물함' 톤 유지.
  • 오프라인/방치 트리클은 상한 캡(12시간 권장) 두고 전체 수급의 10% 이하 보조 채널로만. localStorage 타임스탬프라 시계조작 치팅 원천봉쇄 불가하나, 판돈 작게 설계하면 치팅 실익 없음 — 서버검증 없이 클라이언트 clamp(음수/과대 elapsed 배제)면 충분.
  • Idle 이벤트(비둘기 쫓기·낮잠 등)는 탭 없이 대기 애니메이션 중 랜덤 트리거되는 보상으로. Neko Atsume식 '안 봐도 알아서 쌓임' 원칙 — 강제 체류시간 요구 안 함.
  • 재화는 단일 소프트 재화 유지. 무과금 도구 앱이라 하드/프리미엄 재화(다이아) 도입 불필요·역효과. 이미 있는 ACORN을 코인 역할로 확장 사용 — 별도 화폐 신설보다 리스크 적음.
  • 다이아몬드·하트는 피할 것: 다이아는 '결제 유도/프리미엄' 뉘앙스라 무과금 도구 신뢰 훼손, 하트는 보통 '목숨/에너지 제한' 의미로 오인되어 좌절감 유발.
  • 첫 구매 경험은 첫 세션(5~10분) 내 가능하게: 시작 시 소량 시드 지급 + 최저가 티어1 아이템은 즉시 구매 가능한 가격으로 설정. 초반 5~10분 이탈률 40~60%라는 온보딩 통계 근거.
  • 업그레이드 티어는 무한 지수형(클리커식) 아닌 유한 4~6단계, 비용배율 1.5~1.8배 지수곡선. 매 티어마다 외형 변화 눈에 띄게(코지 게임 UX 원칙).
  • 마일스톤/업적(첫 고양이 연결, 5마리 모으기 등)은 일회성 큰 지급으로 목표감 부여 — 반복 수급과 별개 채널.
  • 재화 이름은 마스코트+배경(비오옴)과 직결돼야 한다 — 도토리(숲/다람쥐 상징)를 고양이 마스코트+해변/무인도 배경에 쓰면 즉각적 테마 불일치가 발생한다. Idle Acorns/Squirrel Idle Tycoon처럼 '도토리'가 성공한 사례는 전부 숲·다람쥐 세계관에서였다.
  • 하트·별·다이아몬드는 업계 관습상 이미 고정된 의미를 갖는다 — 하트=라이프/호감도, 별=등급·프리미엄 티어, 다이아몬드=유료 하드커런시. 이 관습을 깨고 소프트 재화로 쓰면 유저가 재화 기능을 오인한다(예: 하트를 보면 '이거 다 쓰면 게임 오버?'라고 생각).
  • 결제(IAP)가 없는 게임은 소프트/하드 이중재화를 나눌 이유가 없다 — 이중재화(Neko Atsume 은/금 물고기, Merge Mansion 코인/젬)의 존재 목적은 과금 유도·타임스킵 판매인데, 이 게임엔 그 축이 없다. 단일 재화 + 희귀 등급 변형(마일스톤 보상용) 정도면 충분하다.
  • Cats & Soup처럼 재화를 용도별로 분리(골드=코어루프, 가구코인=꾸미기 전용, 레시피포인트=성장)하면 이름만 보고 용도가 예측되는 정보 스캔 효과가 생긴다. 다만 무과금 소규모 게임에선 재화 종류를 늘리기보다 기존 단일 재화의 소비처(간식/꾸미기)를 다양화하는 편이 관리 비용 대비 효율적이다.
  • 디제틱(diegetic) 재화가 몰입을 깨지 않는다 — Neko Atsume은 '고양이가 고마움의 표시로 물고기를 놓고 감'이라는 세계관 내적 설명이 가능해서 자연스럽다. 이 게임은 고양이+해변이므로 '물고기'가 세계관 안에서 설명 가능한 유일한 후보다(도토리는 해변에 존재할 이유가 없음).
  • 재화 이름은 곧 아이콘 디자인 방향을 결정한다 — 이름을 먼저 확정해야 아이콘 제작 후 재작업(리네임에 따른 리아이콘)을 피할 수 있다.

  • 2부 누락 — 배율 중첩(compounding) 위험 및 검증절차 부재
    needs/objects/persist 3개 스펙이 각자 완결된 '행복도 저하 시 굼뜬 연출' 메커니즘을 제시하지만 서로 대안(택일) 관계인지 명시하지 않았다. 구현자가 세 스펙을 부분적으로 조합(예: needs의 속도배율×objects의 resting배율×persist의 stall시간)하면 슬로우다운이 곱연산으로 중첩돼 스펙 어느 하나가 의도한 것보다 훨씬 심하게 굼뜬 고양이가 나올 위험이 있다. 또한 '실제 startTask/interruptTask/승인처리는 행복도 영향을 받지 않는다'는 핵심 안전조건(직접 코드 확인 결과 현재는 사실)을 보장할 자동테스트나 검증절차가 5개 스펙 어디에도 제안돼 있지 않아, 추후 리팩터링 과정에서 이 경계가 실수로 깨져도 잡아낼 안전망이 없다.
    → 반영: 3개 메커니즘 중 하나만 채택한다고 문서에 명시. tests/rendered-html.test.mjs 또는 별도 유닛테스트에 'happiness 값과 무관하게 startTask 호출 시점이 즉시 발생한다'를 검증하는 회귀테스트 추가를 구현스텝에 명문화.
